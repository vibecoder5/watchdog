# Watchdog

Небольшой монитор ресурсов одного Linux-сервера: Go + SQLite + встроенный Vue UI на русском языке. На сервере нужен только бинарный файл и systemd; Node.js, CDN, Docker и отдельная база данных не требуются.

## Возможности

- CPU, RAM (через `MemAvailable`), swap, заполнение дисков и inode выбранных разделов.
- Предупреждение и критический порог; задержка превышения, гистерезис, ограничение повторов и сообщения о восстановлении.
- Telegram Bot API и SMTP с обязательным проверяемым TLS (`STARTTLS` или implicit TLS).
- Включение отдельных правил и каналов, полное отключение уведомлений, пауза на 1/8/24 часа и автоматическое возобновление.
- SQLite хранит настройки, состояния правил, историю и очередь доставки. История хранится 30 дней, UI показывает 100 последних событий и 200 доставок.
- До трёх попыток доставки: сразу, через 10 и 20 секунд после неудач. В истории видны результат и безопасное описание ошибки. После третьего сбоя доставка помечается как failed; следующее регулярное напоминание создаёт новую доставку.
- Вход по паролю: bcrypt, HttpOnly/SameSite cookies, сессия на 12 часов, защита изменяющих запросов и ограничение попыток входа. Перезапуск завершает сессии.

## Сборка и проверка

Go 1.23 или новее. Зависимости и Vue закреплены; Vue включён в бинарный файл вместе с UI (лицензия в `internal/watchdog/web/VUE-LICENSE`).

```sh
go mod download
go test ./...
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o bin/watchdog-linux-amd64 ./cmd/watchdog
# Для ARM-сервера: GOARCH=arm64
```

PowerShell:

```powershell
$env:CGO_ENABLED='0'
$env:GOOS='linux'
$env:GOARCH='amd64'
go build -trimpath -o bin/watchdog-linux-amd64 ./cmd/watchdog
Remove-Item Env:GOOS, Env:GOARCH
```

На Windows backend и UI запускаются для разработки, но вместо метрик показывается сообщение о необходимости Linux. CI запускает проверки, race detector и сборку для Linux amd64/arm64.

## Установка на сервер

Поддерживается Linux с systemd и доступным `/proc` (например, Debian/Ubuntu). Копируйте бинарный файл для архитектуры сервера и каталог `deploy`:

```sh
scp bin/watchdog-linux-amd64 user@server:/tmp/watchdog-linux-amd64
scp -r deploy user@server:/tmp/watchdog-deploy
ssh user@server
sudo sh /tmp/watchdog-deploy/install.sh /tmp/watchdog-linux-amd64
```

Сгенерируйте хеш пароля длиной 12–72 байта без помещения пароля в историю shell:

```sh
read -r -s -p 'Admin password: ' password; printf '\n'
printf '%s\n' "$password" | /usr/local/bin/watchdog hash-password
unset password
sudoedit /etc/watchdog/watchdog.env
```

Поместите хеш целиком в `WATCHDOG_PASSWORD_HASH`, сохраняя одинарные кавычки. Файл использует синтаксис systemd `EnvironmentFile`, не shell: **не выполняйте `source`**. Укажите нужные каналы:

| Канал | Переменные |
|---|---|
| Telegram | `WATCHDOG_TELEGRAM_TOKEN`, `WATCHDOG_TELEGRAM_CHAT_ID` |
| Email | `WATCHDOG_SMTP_HOST`, `WATCHDOG_SMTP_PORT`, `WATCHDOG_SMTP_MODE`, `WATCHDOG_SMTP_FROM`, `WATCHDOG_SMTP_TO`; при авторизации также `WATCHDOG_SMTP_USER`, `WATCHDOG_SMTP_PASSWORD` |

Создайте Telegram-бота и добавьте его в целевой чат; бот должен иметь возможность отправлять сообщения. Для SMTP используйте `starttls` (обычно порт 587) либо `tls` (обычно 465). Получатель email один; для нескольких адресов используйте почтовую группу. Секреты настраиваются только на сервере, API их не возвращает. После изменения окружения требуется перезапуск.

```sh
sudo systemctl enable --now watchdog
sudo systemctl status watchdog
sudo journalctl -u watchdog -n 50 --no-pager
```

По умолчанию интерфейс слушает `127.0.0.1:8080`. На своей машине откройте туннель:

```sh
ssh -N -L 18080:127.0.0.1:8080 user@server
```

Откройте `http://127.0.0.1:18080`, войдите, включите настроенные каналы и сохраните изменения. Затем отправьте тест из вкладки «Каналы доставки» и проверьте историю.

Для постоянного доступа по HTTPS добавьте сайт из `deploy/Caddyfile.example` в имеющуюся конфигурацию прокси и установите `WATCHDOG_SECURE_COOKIE=true`. Backend оставьте на localhost. Для явно выбранного внешнего bind требуется `WATCHDOG_ALLOW_REMOTE=true`; TLS обеспечивает reverse proxy. Не включайте Secure cookie при использовании HTTP через SSH-туннель.

## Деплой одной командой из PowerShell через Caddy

Подготовьте локальный файл `watchdog.env` по `deploy/watchdog.env.example`: укажите bcrypt-хеш пароля и секреты каналов. Затем из корня проекта выполните:

```powershell
.\deploy\deploy.ps1 -ConfigFile .\watchdog.env -Server 195.133.76.98 -User root -Domain watchdog.u-agent.ru
```

При другом SSH-порте добавьте `-Port 2222`; для ARM-сервера — `-Architecture arm64`. SSH-аутентификация выполняется обычным способом; пользователь должен иметь root-доступ или право `sudo`. Бинарный файл соответствующей архитектуры должен быть собран в `bin/` заранее.

Скрипт загружает бинарный файл и настройки в приватный временный каталог, устанавливает systemd-сервис и копирует настройки в `/etc/watchdog/watchdog.env` с правами 600. Существующие бинарный файл, файл окружения и Caddyfile сохраняются в защищённой резервной копии. База данных и настройки UI сохраняются. Повторный запуск намеренно заменяет файл окружения переданным локальным файлом.

Если `caddy` уже установлен, его установка и обновление пропускаются. Иначе скрипт устанавливает пакет из настроенных apt-репозиториев Debian/Ubuntu. Поддерживается Caddy как systemd-сервис с `/etc/caddy/Caddyfile`; нестандартную установку или уже существующий конфиг этого домена скрипт предлагает интегрировать вручную.

Сайт добавляется отдельным файлом `/etc/caddy/watchdog.caddy` через `import`, остальные сайты сохраняются. Перед reload проверяется конфигурация; при ошибке валидации или reload восстанавливаются файлы Caddy и предыдущая конфигурация watchdog. При неудачном запуске или локальной проверке backend watchdog также откатывается. Backend слушает только `127.0.0.1:18082`; дополнительный файл `/etc/watchdog/https.env` задаёт этот адрес и Secure cookie поверх скопированных настроек. На сервере требуются `curl` и `flock`.

DNS и доступность `watchdog.u-agent.ru` скрипт не проверяет. Проверяется только локальный `/healthz`. Выпуск HTTPS-сертификата выполняет Caddy при запуске сайта; успешное завершение скрипта не подтверждает внешний доступ или получение сертификата. После входа включите нужные каналы в UI.

## Настройки и поведение

По умолчанию проверки идут каждые 15 секунд, напоминания — раз в 60 минут. CPU/RAM: 85/95%, диск/inode: 80/90%, swap: 80/95%. CPU, RAM и swap требуют превышения в течение 60 секунд; диск и inode — 30 секунд. Порог CPU основан на среднем использовании всех ядер между проверками; первая CPU-метрика появится со второй проверки. Отсутствующий swap показывается как 0%.

Гистерезис снимает критический уровень при достижении `critical − hysteresis`, предупреждение — при достижении `warning − hysteresis`. Понижение уровня применяется сразу после достижения границы. Для предупреждения и критического превышения задержка считается отдельно: колебания около критического порога не подавляют предупреждение. Пропущенное измерение или длительный перерыв сбрасывает отсчёт непрерывного превышения. Изменённые правила применяются со следующего измерения; новый интервал — после текущего ожидания.

В паузе метрики и состояния обновляются, но сообщения не создаются. Отключение канала/правила и установка паузы отменяют соответствующие ожидающие доставки; уже начатый сетевой запрос может завершиться. При возобновлении текущая тревога отправляется на следующей проверке. Новое событие метрики отменяет её устаревшие ожидающие сообщения. Если процесс завершился после принятия сообщения провайдером, но до записи результата, после запуска возможна повторная доставка (at-least-once).

Точки монтирования задаются абсолютными путями. Указывайте существующие mount points: путь к обычному каталогу покажет данные файловой системы этого каталога. Диск считается как `1 − Bavail / Blocks`, включая зарезервированные блоки. Пользователь `watchdog` должен иметь право прохода к выбранным путям; выдавать root-права сервису не требуется. Для файловых систем без inode-счётчика эта метрика не показывается. Ошибки чтения видны в UI и дают HTTP 503 на `/healthz`; отдельные сообщения об ошибках коллектора в каналы не отправляются.

`GET /healthz` без авторизации возвращает только готовность процесса; метрики, настройки и история доступны после входа. UI обновляет данные каждые 5 секунд и помечает устаревшие данные. Все даты показываются в часовом поясе браузера.

## Обновление и резервная копия

Повторно запустите `install.sh` с новым бинарным файлом и затем `sudo systemctl restart watchdog`. Установщик сохраняет `/etc/watchdog/watchdog.env` и `/var/lib/watchdog`.

Для согласованной резервной копии остановите сервис и скопируйте весь `/var/lib/watchdog` вместе с защищённым файлом окружения, затем запустите сервис. Перед заменой бинарного файла сохраняйте его предыдущую версию; откат выполняется тем же установщиком. В этой версии схема создаётся при старте; будущие изменения схемы потребуют отдельных миграций.

## Ограничения

Сервис наблюдает сервер, на котором запущен. При полном отключении хоста, сети, самого watchdog либо заполнении его диска отправка может быть невозможна. Для обнаружения таких сбоев нужен внешний наблюдатель, например проверяющий `/healthz`. Нет централизованной панели нескольких серверов и долговременного хранилища графиков. Ресурсы контейнеров отдельно не измеряются.
